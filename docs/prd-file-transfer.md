## 1. 背景

team-mailbox 是团队内部局域网的 Agent 文本信箱：管理员在服务端预配置「来源 IP → 成员名」，成员通过自己 Agent 的 MCP bridge 收发自由文本，中心服务用 SQLite 保存消息。当前已在 `192.168.11.40:18787` 部署，登记成员 4 人。

**当前现象**：系统只支持纯文本。当成员想同步一份排查记录、接口约定或日志片段（常见为 `.md`、`.txt`、`.log`）时，只能让 Agent 读取文件内容、以文本形式发送。

已确认的限制（源码与实测确认）：

- 正文上限 32000 个 UTF-16 码元（`src/config.js` `maxTextChars`）。
- 单次请求体上限 64 KiB（`src/config.js` `maxBodyBytes`）。
- 实测：32001 字符被拒绝（HTTP 400）；24000 个中文（请求体 72028 字节）被拒绝。
- 中文按 UTF-8 每字 3 字节计，实际约 21000 字就会先触发请求体上限。

**为何现在做**：排查场景中经常需要传递超出上述上限的文件，且文本化传输会丢失原始文件名与格式；把长文档拆成多条消息会破坏可读性和上下文。

## 2. 目标

### 2.1 核心目标

|目标|衡量标准|
|---|---|
|支持成员之间直接传输小文件|发送方指定本地文件路径即可发送，接收方可保存到自己指定的本地路径，保存后内容哈希与原文件一致|
|限制单次传输体积，避免中心和局域网被拖垮|单个文件原始大小 > 10 MiB 时明确拒绝，并返回可理解的原因|
|文件权限与现有消息一致|只有接收人能下载附件；发送人和第三方请求一律被拒绝|
|不破坏既有文本能力|现有 5 个工具行为不变，历史消息与已读状态不受影响，现有 30 项自动化测试全部通过|
|保持单文件备份可用|`admin backup`（`VACUUM INTO`）仍可一次性备份含附件的完整数据|

### 2.2 非目标（本次不做）

- 多附件：单条消息只允许 1 个附件。
- 断点续传、分片上传、压缩、去重。
- 群发、公网访问、传输加密（仍是可信局域网内的 HTTP 明文）。
- 病毒扫描、内容审查、附件预览渲染。
- 附件自动落盘：接收方不指定路径时不会自动写文件。
- 对象存储/文件服务器等外部依赖。

## 3. 现状分析

### 3.1 当前业务链路

```Plain Text
发送方 Agent
  → 本地 MCP bridge（src/mcp.js，仅转发，不存储）
  → 中心服务 HTTP（src/server.js，按 socket 来源 IP 识别成员）
  → SQLite messages 表（中心机器 data/msg.sqlite）
  → 接收方 Agent 主动调用 getmsg / read_message 拉取文本
```

### 3.2 当前数据模型

```Plain Text
members(name, display_name, created_at, revoked_at) ← 历史身份，仅用于外键
messages(id, from_name, to_name, title, text NOT NULL, project,
         reply_to, created_at, read_at, device_name) ← 消息本体，text 必填
```

### 3.3 关键问题或现状限制

|编号|问题/限制|简单说明|业务影响|目标结果|
|---|---|---|---|---|
|P1|不支持文件|无附件概念，只有 `text` 字段|`.md`/`.txt` 只能转成文本发送，丢失文件名|支持发送单个文件并保留原始文件名|
|P2|体积上限过小|请求体 64 KiB、正文 32000 码元|中文约 2 万字即超限，长文档必须拆分|文件路径最大 10 MiB|
|P3|接收端无法还原文件|`read_message` 只返回文本|接收方需手动复制粘贴另存|接收方可直接保存为本地文件并校验哈希|
|P4|无完整性校验|文本传输无校验值|截断或粘贴错误不可发现|上传与保存双向校验 SHA-256|

### 3.4 目标业务结果

```Plain Text
发送方："把 D:\notes\排查记录.md 发给利浩文"
  → Agent 调用 send_file，bridge 读取文件并上传
  → 中心校验大小/哈希后入库，返回消息 id
接收方："看看洪伟填发来的未读消息"
  → getmsg 返回消息摘要，并显示附件名、大小
  → "把附件保存到 D:\tmp\排查记录.md"
  → save_attachment 下载、校验哈希、写入指定路径
```

## 4. 方案设计

### 4.1 数据与存储

|编号|改进项|方案|影响范围|
|---|---|---|---|
|D1|新增附件表|新建 `attachments(id, message_id, name, size, mime, sha256, data BLOB, created_at)`，`message_id` 外键指向 `messages(id)`，唯一约束保证一条消息最多 1 个附件|`src/db.js`|
|D2|存储形态|文件二进制直接存 SQLite BLOB，不落地为独立文件|保持 `VACUUM INTO` 单文件备份语义不变|
|D3|历史库迁移|沿用 `CREATE TABLE IF NOT EXISTS` 增量建表；不重建 `messages`，不迁移历史数据|旧库消息、id、已读、回复关系全部保留|
|D4|文件型消息的 text 兼容|`messages.text` 保持 `NOT NULL`；仅发文件时写入空字符串，避免重建表|避免 SQLite 改列约束带来的数据风险|
|D5|摘要回退|`getmsg` 摘要为空时显示 `[文件] 文件名`|`src/db.js` 查询映射|

### 4.2 服务端接口

|编号|改进项|方案|影响范围|
|---|---|---|---|
|S1|发送接口扩展|`POST /api/messages` 增加可选 `attachment {name, mime?, data_base64, sha256}`；`text` 与 `attachment` 至少有其一|`src/server.js`、`src/validation.js`|
|S2|请求体上限分级|仅 `POST /api/messages` 提升到 16 MiB（10 MiB base64 约 13.4 MiB + JSON 开销），其余接口保持 64 KiB|`src/config.js`、`parseJsonBody` 已支持按接口传入上限|
|S3|附件下载|`GET /api/attachments/:id` 返回元数据与 base64 内容，仅接收人可取|`src/server.js`|
|S4|文本预览|`GET /api/attachments/:id/text?offset&limit` 仅对文本类文件且 ≤ 1 MiB 提供分段文本|`src/server.js`|
|S5|服务端校验|解码后字节数 > 10 MiB 拒绝；SHA-256 与内容不符拒绝；文件名去除控制字符并截断至 200 字符|`src/server.js`|
|S6|超时放宽|附件相关请求超时由 10 秒提升至 30 秒，文本接口保持 10 秒|`src/config.js`、`src/mcp.js`|

### 4.3 MCP 工具（新增 3 个，现有 5 个不变）

|编号|工具|方案|
|---|---|---|
|T1|`send_file({to, path, title?, text?, project?, reply_to?})`|bridge 读取本地文件、计算 SHA-256、base64 后上传；返回 `{id, name, size, sha256}`|
|T2|`save_attachment({attachment_id, path, overwrite?})`|下载并校验哈希后写入指定路径；默认不覆盖已有文件；要求绝对路径且父目录已存在|
|T3|`read_attachment_text({attachment_id, offset?, limit?})`|文本类文件分段读取，默认 2000、最多 4000 码元，与 `read_message` 语义一致|
|T4|元数据透出|`getmsg`、`read_message` 返回中增加 `attachment {id, name, size, mime, sha256}` 或 `null`|

文本类判定：扩展名白名单（`.md .txt .log .json .csv .yml .yaml .xml .ini .conf .sql .js .ts .py .sh .ps1`）或 MIME 以 `text/` 开头，且大小 ≤ 1 MiB；其余一律拒绝预览，提示改用 `save_attachment`。

### 4.4 配置项

|配置|默认值|说明|
|---|---|---|
|`MSG_MAX_ATTACHMENT_BYTES`|`10485760`（10 MiB）|单个文件原始字节上限，管理员可下调|
|附件请求体上限|16 MiB|由上一项推导，不单独配置|

## 5. 接口与数据契约

### 5.1 请求字段（`POST /api/messages` 扩展部分）

|字段|必填|约束|
|---|---|---|
|`text`|条件必填|无附件时必填，1–32000 码元；有附件时可省略|
|`attachment.name`|是|1–200 字符，去除路径分隔符与控制字符|
|`attachment.data_base64`|是|标准 base64，解码后 ≤ 10 MiB|
|`attachment.sha256`|是|64 位十六进制，服务端重新计算比对|
|`attachment.mime`|否|≤ 100 字符，仅作展示，不用于安全判断|

### 5.2 响应结构

```json
{"id": 12, "createdAt": "2026-09-21T06:30:00.000Z",
 "attachment": {"id": 5, "name": "排查记录.md", "size": 20480, "sha256": "..."}}
```

`getmsg` 每条消息增加 `attachment` 字段（无附件为 `null`）；`read_message` 同样返回附件元数据，但不含文件内容。

### 5.3 错误分类

|分类|示例|用户提示|处理方式|
|---|---|---|---|
|参数错误|文件名为空、base64 非法、sha256 格式错|`400` + 字段原因|不入库|
|体积超限|解码后 > 10 MiB|`413` + 实际大小与上限|不入库；提示压缩或拆分|
|请求体超限|上传体 > 16 MiB|`413`|连接终止前返回原因|
|完整性失败|SHA-256 不匹配|`400` 提示重传|不入库|
|权限不足|非接收人下载附件|`403`，不区分是否存在以免探测|拒绝|
|对象不存在|附件 id 不存在|`404`|拒绝|
|预览不适用|二进制文件或 > 1 MiB|`400` 提示改用保存|拒绝|
|本地写入失败|目标已存在、父目录缺失、相对路径|bridge 返回 `isError` 与具体原因|不写入、不静默覆盖|

## 6. 技术约束与风险

### 6.1 向后兼容

- 现有 5 个工具的参数与返回结构不变，新增字段为可选新增项。
- 旧版 bridge 连新版中心：可正常收发文本；对含附件消息只看不到附件字段，不报错。
- 新版 bridge 连旧版中心：`send_file` 会因接口不存在而失败，提示升级中心；文本功能不受影响。
- 历史数据库无需迁移脚本，增量建表；升级前仍建议执行一次 `admin backup`。

### 6.2 技术约束

- 单进程、单写者 SQLite：10 MiB 附件写入期间会短暂占用写锁，busy timeout 5 秒。
- base64 使传输体积增加约 33%，10 MiB 文件实际传输约 13.4 MiB。
- 内存占用：单次上传峰值约为原始文件的 3 倍（原始 + base64 + JSON 字符串）。
- 身份仍依赖来源 IP，文件传输不改变信任模型：IP 不等于强身份认证。
- 附件内容属于不可信数据，工具描述需明确禁止据此执行命令。

### 6.3 风险与依赖

|风险|影响|应对|
|---|---|---|
|数据库膨胀|每 100 个 10 MiB 附件约 1 GB，备份变慢|监控 DB 大小；清理策略见待确认事项|
|大文件并发|多人同时传 10 MiB 可能拖慢文本消息|一期靠团队规模自然限流，必要时再加并发限制|
|接收方磁盘写入|误覆盖本地文件|默认禁止覆盖，必须显式 `overwrite`|
|局域网带宽|10 MiB 在慢速链路可能超时|超时放宽至 30 秒，失败后提示重试|

## 10. 已确认决策（2026-09-21 洪伟填确认）

|编号|事项|决策|
|---|---|---|
|C1|10 MB 口径|**原始文件 ≤ 10 MiB**；base64 编码后传输体积随之增大（约 13.4 MiB），按实际值放行，不再压缩口径|
|C2|附件保留策略|**永久保留**，一期不做自动清理；依赖管理员备份与人工维护|
|C3|发送人回看|**不允许**，沿用「仅接收人可读」；发送人请求自己发出的附件同样返回 403|
|C4|admin 统计/清理命令|**不做**，一期不提供 `list-attachments` / `prune-attachments`|
|C5|文件名重名|**不自动改名**，按接收方指定路径保存，已存在时默认拒绝，需显式 `overwrite`|

其余内容按本 PRD 第 4–9 章执行。
