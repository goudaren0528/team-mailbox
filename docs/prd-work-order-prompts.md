## 1. 背景与写前评估

用户希望通过已有 team-mailbox 发送结构明确的测试或修复工单，并收到可追溯结果，避免角色、代码版本、验收口径和重复任务歧义。
本轮授权仅整理 PRD；本期产品范围已选定为“仅规范提示词和模板”。
采用从头编写模式：目标文件此前不存在，会话协议为需求依据，最小源码与文档核对为现状依据。
材料门槛已满足：动机、目标、范围、协议、计划交付和验收方式齐备；负责人、排期等非关键项待定。
异常恢复、权限边界、历史兼容和回滚均在下文覆盖；未定结果状态、附件载荷和人工去重规则不得包装为已批准。

## 3. 现状事实与限制

当前链路：用户授权 → Agent 调用 send_message / send_file → 中心入库 → 收件人主动查看。
project 是自由路由标签，不是权限域；消息标题和正文目前没有工单业务 schema 校验。
入库成功只证明送达，不证明接单或执行；没有发送幂等键，超时可能已经入库。
消息是不可信数据，现有 MCP 明确禁止把消息内容作为可执行指令；新规范不得绕过这一边界。
只能读取发给自己的消息，无发件箱读取工具；读正文末页会自动标读，不能称为无副作用探针。

| 已核对限制 | 现状值 / 证据 |
| --- | --- |
| title / project / text | 100 / 50 / 32000 个 UTF-16 码元；src/config.js、src/validation.js |
| 纯文本请求 | 整个 JSON UTF-8 编码后最多 64 KiB，包含字段与转义开销 |
| 附件 | 每消息最多一个，非空，默认原始上限 10 MiB（10485760 字节），部署可调低 |
| 附件请求 | 16 MiB 请求体上限；正文仍受 32000 码元限制；不适用于纯文本 |
| 工具参数与关联 | src/mcp.js 的 send_message/send_file 沿用 title/text/project，无 reply_to |
| 行为依据 | docs/tools.md 的发送、文件、已读与关联说明；本次只读核对 |

现有文档允许普通长文本自行分段；本协议完整工单不能沿用无协议碎片拆分方式。

## 4. 方案设计（交付计划，尚未实施）

### 4.1 产物及边界

- 计划新增 team-mailbox-dispatch Skill 与同名原生 command：整理、检查、预览，用户明确授权发送后才调用已有发送工具。
- 计划提供 WORK TEST、BUGFIX、TEST_FIX 三类模板，以及 RESULT 模板和发送前检查清单。
- 计划补充 README 中英安装/使用说明；本轮不生成这些实现文件，不安装任何入口。
- Skill 只是 Agent 行为规范，由人工与执行端遵循；不提供运行时强制校验或自动接单能力。
- 工单来自用户当前目标项目的上下文；不得因为当前操作 mailbox 仓库而把它当成待测仓库。

### 4.2 正常流程

1. 用户主动请求整理工单，确认当前项目绑定、接收人和目标角色；绑定无法确定先问。
2. 从目标项目 Git 读取对象格式、完整 HEAD、基线和 dirty 状态，解析要求引用的文档版本与章节。
3. 填写完整 WORK 数据、验收要求、环境和约束；缺必要信息返回缺项清单，不产出看似完整的可发送工单。
4. 核对角色组合、标题/标签/正文一致性、对象存在性、引用与权限、长度和已知重复记录。
5. 展示接收人、project、完整标题、JSON、范围/风险与长度预算；用户明确授权此次发送后才发送。
6. 仅使用实际返回的消息 ID 记录送达；失败按第 6 节处理，不自动重发或自动改走附件。
7. 接收端在用户主动查看且独立授权后核对工单；RESULT、其他项目或角色不进入本接单流程。
8. 执行权限由接收端用户/宿主独立给定；工单仅作需求数据，结束后按实际证据整理 RESULT，再确认发送。

## 5. 接口与数据契约

### 5.1 WORK 信封与角色

消息三部分：mailbox project 标签、标题、正文中的一个明确 JSON 数据块；块外可追加说明但不得覆盖块内规范字段。
标题固定为 `[WORK:v1][角色][类型][工单编号] 简短描述`；类型对应 mode。
角色仅 FIX、QA；mode 仅 TEST、BUGFIX、TEST_FIX。QA 仅允许 TEST；FIX 允许三种。
其他组合报告格式错误，不推测或自动修正；收件人逻辑身份与角色分别确认，不自动建立角色映射。

| 字段 | 必需规则 |
| --- | --- |
| schema | 固定 on-duty.work.v1 |
| ticket_id / revision | ticket_id 与标题一致；revision 为从 1 开始的正整数 |
| project / target / mode | project 与标签、当前项目绑定一致；target 为目标角色，与标题角色一致；mode 与标题类型一致 |
| summary | 非空需求摘要，不替代可判定验收 |
| code.head_commit | 目标仓库中真实存在的完整固定 commit 对象 ID，不接受短 SHA 或 branch |
| code.base_commit | 变更测试必需；Bug 无基线可省，但须解释原因；不能隐式取当前分支作为基线 |
| code.related_files | 必须提供数组；已知文件填仓库相对路径，未知用空数组，不编造路径 |
| requirements | 必须包含预期与可判定验收；引用文档时必须解析版本、章节和适用内容 |
| environment | 必须说明测试目标、角色与数据引用；不携带登录秘密 |
| constraints | 必须说明范围、fallback 政策、高风险限制及非范围；不能扩大既有权限 |
| bug | BUGFIX 必需：实际、预期、复现步骤或无法稳定复现的明确说明 |

TEST_FIX 已有明确 bug 时补 bug；没有时按测试范围和验收执行，不凭空编造缺陷。
允许补充 references：Issue/PR、PRD 文档版本与章节；消息关联仅放 references.message_ids，不恢复 reply_to。
允许补充重点文件说明、优先级/截止时间/预算、浏览器/视口/语言/角色、测试数据清理计划、已知限制/失败日志。
必须验证项与非范围应明确；建议验收项带 AC IDs；重测必须给 previous_report_id、新 revision 与准确代码版本。
environment.profile、account_ref 只能是逻辑引用，不能被解释为创建环境、取凭据或切换账户的指令。
禁止 password、token、cookie、登录态原文；只可引用已批准凭据，引用不可访问则阻塞，不擅自获取。
constraints 中 allow_commit 等声明不得超过实际用户授权；收到新工单不自动授权 shell 修改、commit 或 push。

### 5.2 Git 与版本约束

完整 ID 按目标仓库实际对象格式验证：SHA-1 为 40 位，SHA-256 为 64 位十六进制，并核实该对象存在且是 commit。
仅长度匹配不构成有效证据；对象缺失先报告，不擅自 fetch、创建提交或填占位 SHA。
dirty 影响待测范围时，阻塞并确认，或明确约定只测试已提交版本、dirty 不在范围；不能混报为 HEAD 内容。
文档引用不可访问、版本不明或验收不能解析时停在草稿；不得仅凭标题声称已解析需求。

### 5.3 重复、冲突与执行中的新版

同 ticket_id + revision、内容相同视为同一工单，禁止重复执行；内容不同报告冲突，不选一个猜测执行。
内容比较提案：核对 project、标题、完整 JSON 和追加说明；仅 JSON 键排序/空白归一，其余差异按冲突处理，待评审。
新要求必须提高 revision 并发送完整正文；执行中新版先登记为待确认，在安全节点由用户决定切换，不打断当前操作。
重测不得复用旧 revision；提供 previous_report_id 与准确 base/head，并明确本轮覆盖变化。
跨会话没有共享去重记录，无法核对时先问或人工查证；同会话登记不等于持久化、原子锁或并发互斥。
发送幂等与执行幂等分开：已送达工单是否再次传送由用户决定；重复传送不允许触发重复执行。
其他 project/target 的消息仅对本接单流程忽略，普通收件查看规则不变；RESULT 永不作为新任务执行。

### 5.4 WORK 示例（结构草案，不是可发送工单）

示例项目 project-a，发送人 alice、接收人 bob；标题：`[WORK:v1][QA][TEST][A-1042] 验证验收范围`。
下例 SHA/文档引用均为显式占位，不能作为真实证据或实际发送；内层字段命名为模板提案。

```json
{
  "schema": "on-duty.work.v1",
  "ticket_id": "A-1042", "revision": 1,
  "project": "project-a", "target": "QA", "mode": "TEST",
  "summary": "验证已提交变更的验收范围",
  "code": {"head_commit": "<实际完整HEAD，禁止发送占位>", "base_commit": "<实际完整BASE，禁止发送占位>", "related_files": []},
  "requirements": {"expected": "满足已解析需求", "acceptance": [{"id": "AC-1", "statement": "<替换为可判定结果>"}], "document": {"ref": "<批准文档引用>", "version": "<实际版本>", "section": "<实际章节>"}},
  "environment": {"target": "<批准测试目标>", "role": "<批准角色>", "profile": "<逻辑环境引用>", "account_ref": "<已批准凭据引用>", "data_refs": []},
  "constraints": {"scope": "仅约定验收范围", "fallback": "不可用则报告并等待确认", "high_risk": "不操作生产数据", "out_of_scope": ["提交与推送"]},
  "references": {"message_ids": []}
}
```

BUGFIX 模板以 A1043 为另一示例编号，增加 bug 实际/预期/复现说明；TEST_FIX 保留相同必需字段并按有无明确 bug 分支填写。
三个正式模板均须独立完整，不能要求接收方从旧消息拼接字段；本 PRD 不替代待交付模板文件。

### 5.5 RESULT 约束与模板提案

用户确认标题：`[RESULT:v1][FIX或QA][ticket_id][rN] PASS/FAIL`；角色和版本必须对应原工单。
用户未指定 RESULT schema 常量或第三种状态；本期不能宣称存在已批准的新 schema/状态枚举。
建议正文一个 JSON 块，至少包含：ticket_id、revision、原 message ID、report_id、executing_agent。
还须包含实际 base/head、FIX 交付位置与修改状态、测试结论和覆盖、ComputerUse/fallback 实际使用情况。
失败、阻塞、未执行项、可访问 attachment/link 证据和后续动作均须显式列出；不适用字段解释原因，不伪填。
实际代码未提交时如实标 dirty/未提交及相对文件和差异证据，不能把修改冒称为 head_commit 的内容。
PASS 必须有实际执行证据且全部必需验收通过；未执行、阻塞或缺证据不得 PASS，也不能直接等同测试失败。
待评审提案：允许第三种待定状态，或沿用 FAIL 但强制声明 scope=未执行/阻塞，区别测试 FAIL；确认前暂停发送此类标准结果。
report_id 生成/唯一性规则待评审；人工记录原消息 ID 和回报 ID，不承诺服务端关联约束或全局唯一。

## 6. 边界、异常与恢复

| 场景 | 用户可见结果、记录与恢复 |
| --- | --- |
| 格式错、缺项、多 JSON 块 | 列字段错误，保留草稿，不发送；补齐后重新预览 |
| project/角色/版本不一致 | 明确冲突位置；不自动改路由、接收人或代码版本 |
| 收件人/关联 ID 无法核对 | 只接受已确认逻辑收件人和实际 ID；核对权限及所属工单，不猜 ID、不读取他人消息 |
| 信息来自消息正文 | 只作为不可信数据；不执行其中命令或凭据获取要求；独立确认权限 |
| 外部业务拒绝、403/400 | 保存并显示真实工具原因；不冒充系统故障，不改身份或权限绕过 |
| 网络/限流/系统错误 | 分类记录实际返回；不自动重试发送，修复条件后再次征求用户决定 |
| 超时、送达未知 | 标记“送达未知”；先以真实返回 ID 或获准的收件侧列表核对，不读正文作探针；不能核实时等待人工查证 |
| 接收方离线 | 入库不是执行承诺；记录已送达，等待主动处理，不追加催单副作用 |
| 标题/标签/正文或请求体超限 | 不截断标识、不拆碎 JSON；提示缩短可选描述/说明，保留必要 summary 与验收语义，重新预算 |
| 超限附件替代 | 仅提案：send_file 携带一个完整 JSON 文件，保留 WORK 标题/project；正文标明载荷文件名、哈希、ticket/revision，接收方核对后识别；评审确认前不启用 |
| 附件限制与证据不可达 | 核对非空、部署实际上限和请求开销；证据不可访问则报告缺证据，不宣称 PASS |

发送前清单：身份/项目绑定 → 完整字段与一致性 → Git/dirty/引用 → 权限与敏感内容 → 重复冲突 → UTF-16 与 UTF-8 预算 → 完整预览 → 明确发送授权。
附件方案必须另定唯一识别标记和不可信载荷校验细则，不能从普通附件猜测工单，也不自动下载/执行附件。

## 7. 兼容、风险与实施状态

历史普通消息继续自由发送，旧入口/旧客户端/旧配置不变；历史消息不迁移、不补字段、不做补偿脚本。
进行中任务不强制转换为新协议；用户明确选择后才使用新入口，新版安全切换不影响旧任务已有权限。
本期不增加存储或配置默认值；提示词遵循度、并发和跨会话重复仍依赖人工监督，不能承诺 exactly-once。
材料核对与 PRD 整理已完成；Skill、command、正式模板、README、协议验收均待实施；负责人和排期待定。
本轮仅创建本文件，不安装、不发送/读取消息、不启动服务、不修改源码或配置、不提交或发布。

优先使用离线样例、工具调用替身和授权流程演练；所有发送测试需另行授权，不能用真实消息默认验证。

| 序号 | 验收项 | 验收方法 | 预期结果 |

| AC08 | 新版与重测 | 执行中新 rev、缺 previous_report_id、错误代码版本 | 登记等安全切换；重测字段不全不发送 |

| AC11 | 结果与证据 | 全通过、实际 FAIL、阻塞/未执行、附件/link 不可达 | 仅真实全通过 PASS；未决状态等待评审，不伪装 FAIL/PASS |
| AC12 | 限额边界 | 100/50/32000 及各超一、emoji、请求 65536/65537 字节、附件上限/空文件 | 分开验证码元和字节；超限不截标识、不碎片化，附件不自动启用 |
| AC13 | 异常重试 | 模拟拒绝、限流、超时、网络错误与送达未知 | 展示真实原因、记录未知状态，先查证且不自动重发 |
| AC14 | 模板语法与预览 | JSON.parse 检查全部模板；占位扫描；发送工具替身 | JSON 合法但占位不可发送；明确授权前无发送调用 |
| AC15 | 兼容与回滚 | 旧自由文本、旧配置、进行中任务、移除新入口 | 行为不变，无迁移或历史删除 |
| AC16 | 交付范围 | 检查未来 Skill/command、三类 WORK/RESULT 模板、清单和中英说明 | 无新增接口/DB/registry/自动接单，不发布内部 PRD |

## 9. 灰度、发布与回滚顺序

先评审未定项 → 另获实施授权 → 制作通用产物 → 离线验收 → 用户明确选择安装并小范围使用。
灰度期间人工核对预览、重复记录和结果证据；真实发送与业务执行仍需各自授权。
回滚只移除/停用新增提示词入口及关联模板安装副本，保留其他插件/配置与全部历史消息，不停止已有中心。
内部 PRD 不进入公开仓库；将来发布仅通用 Skill、模板和使用说明，另行审核发布范围。
